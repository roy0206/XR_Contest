# 2026-08-08 · Core.Audio 모듈 검증

## 세션 범위

Playground(`D:\Unity\Playground`)의 범용 오디오 모듈을 IUM에 가져와 ISSUE-002의 조치 후보로
시험할 수 있게 만들었다. **기존 시스템은 하나도 수정하지 않았다.**

신규 (전부 `Assets/@Developers/RYU/Audio/`): `Core/` 7개, `Integration/` 4개, `Editor/` 1개,
`README.md`.

미수정: `Assets/@Scripts/Cores/AudioManager.cs`, `Data/DataManager.cs`,
`Dialogue/DialoguePlayer.cs`, `AI/AiVoicePlayer.cs`, `Editor/DevSceneBuilder.cs`.

기록 규칙은 [00 기록 규칙](00_기록_규칙.md)을 따른다.

## 다룬 이슈

- **ISSUE-002** (대사 전용 믹서 채널 없음) — 해결. 리드 프로그래머가 동작을 확인하고 종결을 결정했다. 대사 전용 DSP는 요구하지 않는 것으로 정해, 믹서 자산을 만들지 않고 `Core.Audio`의 DIALOGUE 버스를 대사 볼륨 권한으로 삼는다.
- **ISSUE-015** (신규) — 대사 재생 경로가 아직 새 버스로 전환되지 않았다. ISSUE-002의 설계 판단이 끝나고 남은 적용분이다.

## 왜 "믹서 채널 추가"가 아니게 되었나

[누적 이슈 정리](2026-08-08_이슈_정리.md)에서 확인한 대로 프로젝트에 `.mixer` 자산이 없다.
그래서 원래 조치는 믹서 자산 생성부터였는데, 리드 프로그래머가 Playground의 범용 오디오
모듈을 후보로 지정했다.

그 모듈은 **Unity AudioMixer를 쓰지 않는다.** 버스별 볼륨을 `AudioVolumeMixer`가 직접 곱한다.
따라서 ISSUE-002가 지적한 두 가지 중 하나만 해소된다.

| 지적 사항 | 이 모듈로 |
|---|---|
| 대사 재생 코드가 지점마다 중복 | 해소. 볼륨 권한이 버스 하나로 모인다 |
| 대사에만 이펙트·일괄 감쇠 | 절반. 더킹은 버스 볼륨으로 되지만 DSP 필터는 불가 |

**대사에 DSP가 필요한지 기획 확인이 선행되어야 이슈를 닫을 수 있다.** 필요 없다면 이 모듈로
종결 가능하고, 필요하다면 믹서 자산이 별도로 있어야 한다.

## 이식하며 확인한 것

### 구 AudioManager와의 실제 델타는 작다

채널 풀, BGM 레이어, 반복 재생, 오래된 비반복 SFX 회수, `Update` 순회는 신 버전이 상위
호환이다(`Sequence` 기반 회수, 뮤트, 초기화 경고가 더 있다). 구 버전에만 있던 것 중 실제로
이식한 것은 **`spatialize` 한 줄**뿐이다.

`AudioMixer` 연동(`MASTER`/`SFX`/`BGM` 파라미터, dB 변환, `outputAudioMixerGroup`)은 이식하지
않았다. 믹서 자산이 없어 지금도 죽은 코드다. `ApplyVolume`이 `mixer == null` 폴백으로
`AudioListener.volume`만 건드리고 있었다.

호출부는 `DataManager.cs:79-83` 한 곳뿐이라 정식 교체 시 비용이 거의 없다.

### 네임스페이스 함정 — `Singleton<T>`

IUM과 Playground 양쪽에 전역 `Singleton<T>`, `AudioManager`, `Module`, `MonoThing`이 있다.
namespace 격리로 대부분 해결되지만 `Singleton<T>`만은 그것으로 부족하다.

```csharp
using Core.Foundation;                       // 파일 최상단
namespace Core.Audio
{
    class AudioManager : Singleton<AudioManager> { }   // IUM 것이 선택된다
}
```

C# 이름 조회는 네임스페이스 멤버를 using 지시문보다 먼저 본다. 전역 네임스페이스에 IUM
`Singleton<T>`가 있으므로 무자격 참조는 그쪽으로 붙는다. IUM 쪽 제약이
`where T : MonoBehaviour`라 **컴파일이 통과하고**, 지연 생성 동작까지 따라와 런타임에야
드러난다.

`Core.Foundation.Singleton<AudioManager>`로 완전 수식했고 두 파일에 주석을 남겼다.

### 대사는 Module로 분리했다

`Core.Audio.AudioManager`는 문자열 ID로 사전 로드된 클립만 재생한다. 대사 음성은 Addressables
녹음 → 실패 시 TTS 합성 → 실패 시 무음의 3단 폴백이라 ID로 등록할 대상이 없다. 특히 이음이
응답은 런타임 생성 클립이다.

그래서 `AudioClip` 직접 재생 API를 범용 매니저에 넣지 않고, `DialogueAudioModule`이 자기
`AudioSource`를 들고 볼륨만 `Mixer.Calculate(AudioBus.Dialogue, ...)`로 받아 가게 했다. 범용
매니저에 들어간 대사 관련 코드는 **버스 enum 값 하나와 위임 프로퍼티 둘**뿐이다.

클립 소유권은 모듈이 갖지 않는다. Addressables 핸들 해제와 합성 클립 `Destroy`는
`DialogueVoiceLibrary`가 추적하므로 모듈이 `Destroy`하면 이중 해제가 된다.

### 모듈 호스트를 따로 둔 이유

`Module`은 `MonoThing`에 붙는데 `Core.Audio.AudioManager`는
`Core.Foundation.Singleton<AudioManager>`를 상속한다. 둘 다 `MonoBehaviour`라 C# 단일 상속에서
겸할 수 없다. `Singleton<T>`를 `MonoThing` 파생으로 바꾸면 `SceneController` 등 다른 싱글턴
전체에 파급되므로, 별도 `DialogueAudioHost : MonoThing`을 두고 모듈이 매니저를 생성자로 받는
구성을 택했다.

Playground `Core.Modules`는 가져오지 않았다. IUM `Module`이 이미 `LocomotionModule`·`ViewModule`
등에서 쓰이고 있고, 가져오면 `Module`·`MonoThing` 이름 충돌이 2건 더 늘어난다.

`AddModule` 뒤 `Init()` 호출이 필수다. `Module.TickUpdate`가 `IsInitialized`일 때만 `OnUpdate`를
부르므로 빠뜨리면 재생 종료를 영영 감지하지 못한다.

## 검증 방법

`IUM > Dev > Create Core Audio Test Scene` 후 실행한다. 키 목록은
[README](../../@Developers/RYU/Audio/README.md)에 있다.

`2`(런타임 생성 클립)를 재생한 채 `[` `]`로 대사 볼륨만 움직이는 것이 핵심 확인 지점이다.
사전 등록 없이 만들어진 클립이 DIALOGUE 버스를 타는지를 본다.

실제 `DialogueVoiceLibrary`를 태우지 않은 이유는 그쪽이 Addressables 주소와 AI 설정을 요구하기
때문이다. 클립의 출처 성격만 같게 맞췄다.

## 임시로 남긴 것

`CoreAudioBridge.Update`가 매 프레임 `DataManager` 설정을 따라간다. `VolumeOptionsPanel`이
`DataManager.ApplyAudioSettings`를 부르는데 그 메서드가 아직 구 `AudioManager`만 갱신하기
때문이다. `DataManager`를 수정하지 않고 옵션 슬라이더 반응을 보려면 이 방법뿐이었다.

정식 채택이 결정되면 `ApplyAudioSettings`가 이 버스를 직접 쓰게 하고 그 `Update`를 지운다.

## ISSUE-015 · 대사 재생 경로가 아직 새 버스로 전환되지 않았다

| 항목 | 내용 |
|---|---|
| 발견일 | 2026-08-08 |
| 상태 | 미해결 |
| 위치 | `Assets/@Scripts/Dialogue/DialoguePlayer.cs:139-144`, `Assets/@Scripts/AI/AiVoicePlayer.cs:36-42`, `Assets/@Scripts/Data/DataManager.cs:76-84` |
| 관련 | ISSUE-002, ISSUE-008, `Assets/@Developers/RYU/Audio/README.md` |

**증상**

ISSUE-002가 DIALOGUE 버스 채택으로 종결됐지만, 실제 대사 재생 지점은 아직 구 경로를 쓴다.
`DialoguePlayer.ApplyVolume`과 `AiVoicePlayer.ApplyVolume`이 각각 `DataManager`에서
`DialogueVolume`을 읽어 `AudioSource.volume`에 직접 넣는다. 새 버스를 소비하는 것은 현재
`DialogueAudioModule` 하나뿐이고 그것은 테스트 씬에서만 돈다.

`DataManager.ApplyAudioSettings`도 구 `AudioManager`만 갱신한다. 그래서 `CoreAudioBridge`가
매 프레임 설정을 따라가는 임시 코드를 들고 있다.

**영향**

지금 동작에는 문제가 없다. 대사 볼륨은 두 경로 모두 같은 저장 값을 읽으므로 결과가 같다.
다만 ISSUE-002가 지적한 중복이 그대로 남아 있어, 이슈가 닫혔음에도 코드 상태는 아직
그 이전이다.

**조치 방향**

`DataManager.ApplyAudioSettings`가 `Core.Audio` 버스를 직접 쓰게 하고,
`DialoguePlayer`·`AiVoicePlayer`의 개별 볼륨 적용을 `DialogueAudioModule` 경유로 바꾼다.
그 뒤 `CoreAudioBridge.Update`를 제거한다.

구 `AudioManager`를 대체할지는 함께 결정한다. 호출부가 `DataManager.cs:79` 한 곳뿐이라
교체 비용 자체는 작다.

`AiVoicePlayer`를 손대는 김에 ISSUE-008(일시정지 미대응)도 같이 처리할 수 있다.
`DialogueAudioModule`은 이미 `PauseService.IsPaused`를 본다.
